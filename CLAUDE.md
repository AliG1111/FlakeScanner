# CLAUDE.md — Flake Scanner

iPhone app (SwiftUI, iOS 17+, iPhone only; scanner role on the iPhone 17 Pro Max) that watches the strands ("flakes")
moving past on an OSB forming line and measures their angle to the machine direction (MD), with live and recorded
statistics. Accuracy before speed: the user sets the shots (analyzed frames) per second and drags a box to set the
region of interest (ROI). Methods: *Flake edges* (LSD-style straight edges with collinear merging, default) and *Edge
orientation* (structure tensor). MD is detected from the mat's movement. A second iPhone controls the scanner over
direct phone-to-phone Wi-Fi (Phone LiDAR's remote link, plus a live preview and ROI drawing on the remote).

State: planning (P0.1) in the M0 docs review (`docs/reviews/2026-11-23-M0.md`, cycles 1–2 fixed, cycle 3 next); the GitHub
repository is `AliG1111/FlakeScanner` (P0.2 done); the app skeleton and CI (P0.3, P0.4) are in PR #1 from `p0-skeleton`
(CI green, change review clean), waiting for the owner's merge.

## Hard constraints
- No Mac and no local Swift toolchain. Never try to compile or run Swift here. GitHub Actions is the compiler.
  The Python lab (`tools/lab`) does run here.
- The Xcode project is generated by XcodeGen from `project.yml`. Never commit an `.xcodeproj`.
- Camera, LiDAR and the peer-to-peer radio work only on a physical iPhone. The simulator runs pure logic only; keep
  device-only code out of the test target.
- Builds stay warning-free (0 warnings). A new warning is a defect to fix, not to suppress.
- Accuracy before speed (owner): never lower resolution or analysis quality to reach a frame rate; skip shots and show
  the achieved rate instead. Measurement code is pure and deterministic.
- Repository hygiene (plan: public repo): never commit secrets, Apple IDs, keys, certificates, profiles, personal data,
  local paths, plant photos or video, saved frames or run data. The lab uses synthetic images only.
- Keep on-disk formats readable by new builds (`Run.json` `formatVersion`; new `Codable` fields Optional).
- Push only your own branch. Never push to `main`. Do not merge PRs unless the owner or orchestrator asks.

## Build and test
- CI (from P0.4): workflow `Build iOS app` on `macos-26` (Xcode 26.x) for pull requests into `main`, pushes to `main`
  and by hand. Jobs: `unsigned-ipa` (artifact `FlakeScanner-unsigned-ipa-<run>`), `unit-tests` (scheme
  `FlakeScannerTests`, newest iPhone simulator), optional `testflight`. Build number = run number. The test target
  compiles the pure files listed in `project.yml`; add a file there when it gets tests.
- `gh` works through the REST API only (`gh api repos/AliG1111/FlakeScanner/...`; `gh pr create` uses GraphQL, so open
  PRs with `gh api repos/AliG1111/FlakeScanner/pulls -f title=… -f head=<branch> -f base=main -F body=@<file>`). CI:
  `gh workflow run "Build iOS app" -R AliG1111/FlakeScanner --ref <branch>`, `gh run list -R AliG1111/FlakeScanner
  --branch <branch> -L 3`, `gh run watch <id> -R AliG1111/FlakeScanner --exit-status`, `gh run view <id> -R
  AliG1111/FlakeScanner --log-failed`.
- Pushes that change only Markdown files (`**.md`) start no build (`paths-ignore`, as in Phone LiDAR); docs-only
  changes need none.
- Lab: `pip install -r tools/lab/requirements.txt`, then `python3 -I tools/lab/flake_lab.py [--quick] [--only E9]`.
  Results of record: `python3 -I tools/lab/flake_lab.py --images 8 --json tools/lab/results-<date>.json | tee
  tools/lab/results-<date>.txt` (about 11 minutes).
- Traceability: `python3 -I tools/docs/check_trace.py` after any change to requirement IDs or plan task lines; it must
  report 0 problems (`--fix` rewrites the requirements' phase column from the plan).
- Git proxy: on HTTP 429 wait 5 s and retry once.

## Review protocol
- Severity: Critical (crash, data loss, privacy exposure, wrong measurement in output files or shown as valid) › High
  (wrong results in common use, thread-safety bug, leak during capture, CI break) › Medium (edge cases, missing error
  handling, performance that affects use) › Low (maintainability, polish).
- Cycle: review → triage → fix → CI green → re-review the fix diff; repeat until a review yields no new findings of any
  severity (owner's rule). Critical/High/Medium always fixed; a Low fixed or logged in P11 with a reason.
- Change review: one fresh Opus 5.5 / high reviewer per PR (diff plus callers/callees). Area-split first review for
  the measurement core (P1–P2) and the ported remote link (P6). Milestone final review: one fresh Opus 5.5 / max pass
  over code, tests and guide; its code findings re-reviewed at Opus 5.5 / high.
- Record each review in `docs/reviews/<YYYY-MM-DD>-<milestone or phase>.md` (ID, severity, file:line, summary, status).

## Coding conventions
- Units in names: `_deg`, `_px`, `_mm`, `_s`, `_pxPerS`, `_mmPerS` (or a doc comment). Degrees at API boundaries and in
  files; radians only inside maths.
- Angles (design §6.1): buffer angle β = atan2(dy, dx) with y down (clockwise-positive on screen); flake angle
  θ = wrap(β_MD − β_flake) to (−90°, 90°], counter-clockwise-positive from MD as seen from above; files keep θ in (−90°, 90°] plus the signed deviation
  dev = wrap(θ − target), and the screens show (target − 90°, target + 90°] (requirements §4.1). Always convert through
  `AngleFrame`; never re-derive the sign.
- Axial data: average angles only through `AxialAccumulator` (doubled angles). Never average raw angles.
- Frames stay in sensor landscape (connection rotation 0). Portrait mapping as Phone LiDAR: buffer x = top → bottom,
  buffer y = right → left. The ROI is a `NormalizedRect` in buffer coordinates.
- Determinism: no clocks or random numbers in measurement code; tests and `SyntheticMat` use the seeded PCG generator;
  fixed iteration order (no reductions over `Set`/`Dictionary`).
- Image tests (NFR-TST-02) are of two kinds: parity with `tools/lab` reference results on its small fixture images,
  and accuracy against the truth of mats rendered by `SyntheticMat` with the NFR-ACC-02 tolerances. Lab angles are image
  angles (clockwise-positive): flip the sign of lab means (θ = −β) when exporting fixtures. Change reference results or
  tolerances only with a PR note saying why.
- Threading (design §5): UI and `@Observable` models are `@MainActor`. Camera frames, motion and shot selection on
  `flakescanner.capture.data`; session control on `flakescanner.capture.session`; analysis on `flakescanner.analysis`;
  files on `flakescanner.run.io`; preview JPEGs on `flakescanner.preview`; network on `flakescanner.remote.link`.
  Values cross queues; copy the ROI out of a camera buffer instead of holding it; live snapshots are coalesced (latest
  value, ≤ 4 Hz). `@unchecked Sendable` only for immutable or queue-confined types, with a comment.
- Remote link (as Phone LiDAR): network code only in `Remote/`; values from the other phone are untrusted (check sizes,
  ROI bounds, parameter ranges, frame limits before reading; no traps on peer input); no file sends during a run.
- Files: CSV through `CSV.make`, numbers via `String(format:)` (never localized), JSON via the shared pretty encoder,
  metadata written `.atomic`. File names are constants (`Run.json`, `Frames.csv`, `Samples.csv`,
  `FrameHistograms.csv`, `Histogram.csv`, `Summary.json`, `Summary.csv`, `Frames/`, `TargetReport.json`,
  `TargetFlakes.csv`, `Snapshot.json`); folders are `Runs/run_<yyyy-MM-dd_HHmmss>`, `Snapshots/snapshot_<…>` and
  `Diagnostics/diag_<…>` in Documents (design §7.2). Document every new file in design §7 and the user guide.
- Errors: user-facing `LocalizedError`; no `try?` on paths that read or write measurement data; never delete captured
  data on failure.
- Accelerate (vImage, vDSP, vForce) for convolution, FFT and reductions; plain Swift with unsafe buffers for region
  growing. No third-party packages without a design decision.
- Keep files focused (split beyond ~800 lines), doc comments on non-obvious maths, no force unwraps on file, device or
  peer data, no debug `print`.
